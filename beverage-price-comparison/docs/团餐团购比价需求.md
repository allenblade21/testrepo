# 餐厅团餐 / 团购比价 · 需求文档（新垂直 PRD）

- **文档版本**：v0.1（立项草案）
- **状态**：评审中
- **定位**：在现有「饮品即时零售比价」之外，新增**餐厅到店团购套餐 / 多人团餐**的跨平台比价垂直
- **关联文档**：[真实上线需求文档.md](真实上线需求文档.md) · [设计文档.md](设计文档.md) · [决策记录.md](决策记录.md)

> ⚠️ 这是一个**新品类垂直**，不是饮品比价的小改。平台集、可比单元、到手价口径、匹配难度都与饮品显著不同。本文档界定它的独立需求，并说明可复用与需新建的边界。

---

## 1. 背景与问题

到店餐饮的**团购套餐 / 代金券**是本地生活的高频消费，但同一家餐厅、同一份「3-4 人套餐」，在**美团/大众点评、抖音、口碑**等平台上：

- **团购价不同**（平台补贴、神券、直播间专享价、限时秒杀差异大）；
- **套餐内容不同**（各平台自行组合菜品/份量/赠品，命名也不同）；
- **使用规则不同**（有效期、可用时段、是否需预约、是否含包间费/服务费、能否叠加代金券）。

用户很难判断「同一家店、我这桌人数，团哪个平台的哪个套餐最划算」。本垂直解决的正是这个决策。

## 2. 名词界定

| 名词 | 含义 |
| --- | --- |
| **团购套餐（Deal）** | 餐厅在平台上架的预付套餐，含菜品清单、适用人数、团购价、门市价、使用规则 |
| **代金券（Voucher）** | 「N 元代 M 元」的抵用券（如 100 元代 130 元）|
| **团餐** | 本 PRD 指**多人聚餐/企业聚餐场景**下的多人套餐（按人数选套餐、算人均），非「企业大宗配餐」（后者见 §11 未决）|
| **核销价** | 用户买券后到店实际结算的口径（团购价即核销，或团购券 + 到店补差）|
| **门市价 / 划线价** | 平台展示的「原价」，是**合规敏感项**（见 §9）|
| **神券 / 直播价** | 平台大额补贴券或直播间专享价，时效性强 |

## 3. 目标与范围

### 3.1 目标

用户按**餐厅 / 菜系 / 用餐人数 / 位置**搜索，得到**同餐厅跨平台的团购套餐比价**，以**人均到手价**和**使用规则透明**为核心，辅助「团哪个平台哪个套餐」的决策。

### 3.2 平台集（与饮品垂直不同）⭐

初期接入到店团购主流平台：**美团 / 大众点评、抖音（生活服务）、口碑（阿里本地生活）**。
> 注意：这与饮品即时零售的「阿里闪购 / 京东 / 美团」**不是同一组平台**。团购是独立的数据源与授权体系（各平台生活服务开放能力），本垂直需单独的授权与合规评审。

### 3.3 初期范围

| 维度 | 范围 |
| --- | --- |
| 平台 | 美团点评 + 抖音 + 口碑（先接 1~2 家跑通匹配）|
| 品类 | 到店正餐/火锅/烧烤等**套餐类目**（先聚焦「多人套餐」，代金券二期）|
| 人数 | 支持按 2 人 / 3-4 人 / 5-6 人 / 更多 档筛选 |
| 城市 | 1 个试点城市核心商圈（复用饮品垂直的商圈网格模型）|

### 3.4 本期不做

在线支付/核销、企业大宗团餐配送、菜品评价 UGC、跨城、堂食即时排队。

## 4. 与现有系统的关系（可复用 vs 需新建）

**可直接复用**（架构红利）：
- **可插拔适配器层**：新增团购平台适配器，业务层不变；
- **同商户比价约束**：团购比价同样限定「同一餐厅门店」跨平台，商户边界三层保障沿用；
- **定位 / 商圈网格 / 地点排名骨架**：餐厅按位置召回与排名直接复用；
- **到手价引擎的「规则驱动 + 减免封顶 + 明细透明」范式**；
- **导出 PDF / 界面框架 / 生产化（刷新/限流/可观测）**。

**必须新建**：
- **团购可比单元模型**：`Deal`（套餐）而非饮品 SKU——含菜品清单、人数、使用规则；
- **套餐跨平台语义匹配引擎**（§6，本垂直最大难点，条码在此无效）；
- **团购到手价口径**（§7，含核销价、代金券、直播价、包间/服务费）；
- **团购平台适配器 + 授权/合规**。

## 5. 核心用户故事

1. 我和 3 个同事想吃火锅，搜「附近火锅 4 人套餐」，看到附近餐厅按位置+性价比排列；
2. 点开某餐厅，看到它的「4 人套餐」在美团/抖音/口碑三平台的**人均到手价**并排对比，标出最划算方；
3. 每个套餐清楚列出**菜品清单、有效期、可用时段、是否需预约、是否含包间费**，我不会买了才发现「周末不可用」；
4. 有平台在搞直播专享价，界面标注「限时/直播价，X 分钟前」并提示时效风险；
5. 我把三平台对比导出成 PDF 发到同事群，让大家一起定。

## 6. 功能需求

### 6.1 搜索与召回（M）
- **FR-G1** 支持按 **餐厅名 / 菜系 / 用餐人数 / 位置** 搜索团购套餐；模糊 + 相关度排序 + 分页（复用现有搜索）。
- **FR-G2** 按**用餐人数**筛选（团餐核心维度）：选「4 人」只召回适用 3-5 人的套餐。
- **FR-G3** 地点过滤：只显示用户位置可达/该商圈的餐厅（复用商圈网格）。

### 6.2 同餐厅跨平台套餐比价（M，核心）
- **FR-G4** 对齐**同一餐厅**在各平台的**同类套餐**为一个可比单元（匹配见 §6.5），并排展示各平台**团购价 / 人均到手价**，标注最划算方与节省额。
- **FR-G5** 人均到手价 = 套餐到手价 ÷ 适用人数（人数区间取中值或用户所选人数）。
- **FR-G6** 商户约束：比价单元内所有套餐必须同一餐厅门店（沿用三层保障 + 跨门店 409）。

### 6.3 使用规则透明（M，团购特有）
- **FR-G7** 每个套餐必须展示结构化**使用规则**：有效期、可用时段（如仅工作日/避开节假日）、是否需预约、每桌可用张数、是否含包间费/服务费、能否叠加代金券、退款政策。
- **FR-G8** 规则冲突显著提示（如「本套餐周末及节假日不可用」红色标注），避免「买了不能用」。

### 6.4 菜品与份量对比（S）
- **FR-G9** 展示套餐**菜品清单与份量**，支持同餐厅不同平台套餐的**菜品差异对比**（A 平台多一份饮料、B 平台多两个菜），因为「便宜但少两个菜」不是真便宜。

### 6.5 套餐跨平台匹配引擎（M，最大难点）⭐
条码在团购无效，套餐是**人工组合的非标品**。匹配按多信号：
- **强信号**：同餐厅门店（商户主数据映射）+ 适用人数一致；
- **中信号**：菜品清单集合的语义相似度（菜名归一化/同义词/份量）、价位带接近；
- **产出匹配置信度**：精确 / 疑似 / 仅单平台；低置信进人工标注队列；
- 疑似匹配在界面**明确标注**「套餐内容可能有差异，请核对菜品」，不假装等同。

### 6.6 团餐（多人）辅助（S）
- **FR-G10** 按人数推荐套餐，展示**人均到手价**排序；
- **FR-G11** （二期）多套餐组合建议：人数多时组合两个套餐是否比单个大套餐更划算。

### 6.7 导出与分享（S）
- **FR-G12** 比价结果（含菜品清单、人均价、使用规则）导出为**带时间戳的 PDF**（复用导出能力），便于群内决策。

## 7. 到手价口径（团购版，与饮品不同）

```
套餐到手价 =
    团购价（平台展示价）
  − 平台补贴 / 满减 / 神券（按可叠加规则）
  − 直播间 / 限时专享减免（标注时效）
  + 包间费 / 服务费 / 茶位费（如该套餐/门店收取且不含在内）
  （代金券类：核销价 = 券面抵扣后，需到店补差的另计并提示）

人均到手价 = 套餐到手价 ÷ 适用人数
```
- 规则可配置驱动（各平台补贴/券叠加规则不同）；减免封顶、不得为负（沿用饮品引擎不变式）。
- **核销价与展示价可能不一致**（团购券到店有附加消费）——必须标注口径，避免误导。

## 8. 数据模型（新增）

```
GroupDeal      团购套餐    id, restaurant_id, platform, title, deal_type(套餐/代金券),
                          party_size(适用人数区间), list_price(门市价/分), group_price(团购价/分),
                          menu_items[], usage_rule, valid_from/to, stock/售罄
MenuItem       菜品项      name, spec/份量, qty, is_gift
UsageRule      使用规则    time_windows(可用时段), need_reserve, per_table_limit,
                          extra_fee(包间/服务/茶位), stackable_with_voucher, refund_policy
Restaurant     餐厅门店    id, brand, cuisine(菜系), geo, 商圈网格, rating, 人均, 配送/到店
ComparableDeal 可比套餐单元 id, restaurant_id⭐(单元内唯一), party_size, deals[], match_confidence
Platform(团购) 平台        美团点评 / 抖音 / 口碑（独立于即时零售三平台）
```
> `restaurant_id`（门店）是团购比价的边界字段，等价于饮品的 merchant。

## 9. 非功能与合规（团购特有，硬门槛）

| 类别 | 要求 |
| --- | --- |
| **划线价合规** ⭐ | 门市价/原价展示受《价格法》《明码标价》约束，不得虚构原价制造虚假折扣；「原价」需可溯源，否则不展示原价只展示团购价 |
| **绝对化用语** | 沿用广告法：禁用「最便宜/全网最低」，用「本次比价最低」 |
| 核销一致性 | 展示口径与平台实际核销价偏差需标注；直播/限时价标注时效与失效风险 |
| 数据来源 | 仅用授权的生活服务开放能力；探店视频/图文引流须遵守各平台内容与竞争规则 |
| 匹配可解释 | 疑似匹配必须标注差异，不得把内容不同的套餐伪装成「同款」 |
| 时效 | 团购价含大量限时/直播价，新鲜度要求高于饮品；失效套餐及时下架 |
| 性能/可观测/隐私 | 沿用主系统 NFR（P95、/metrics、PIPL 定位最小化）|

## 10. 匹配质量目标与风险

| 项 | 目标 / 风险 | 应对 |
| --- | --- | --- |
| 套餐匹配准确率 | ≥ 85%（低于饮品，因非标）| 多信号 + 人工标注 + 置信度分级 |
| 内容差异误导 | 高风险：便宜但少菜 | 菜品清单对比 + 疑似标注（FR-G9/6.5）|
| 划线价合规 | 法律风险 | 原价可溯源才展示，法务前置 |
| 直播/限时价失效 | 展示与实际不符 | 强新鲜度 + 时效标注 + 下单前提示 |
| 平台授权范围 | 可能不含套餐菜品明细字段 | 授权谈判按字段清单核对，缺则降级 |

## 11. 里程碑与未决问题

**里程碑**：
| 里程碑 | 内容 |
| --- | --- |
| G-R1 | 单平台团购套餐接入 + 数据模型落地（Mock 先行，复用适配器架构）|
| G-R2 | 套餐跨平台语义匹配 + 置信度分级 + 人工标注台 |
| G-R3 | 同餐厅比价 + 人均到手价 + 使用规则透明界面 |
| G-R4 | 划线价/核销合规评审通过 → 试点发布 |

**未决问题**：
1. 平台集最终范围（是否含快手/小红书本地生活）？
2. 「团餐」是否延展到**企业大宗配餐**（另一套供给与结算，建议独立立项）？
3. 套餐菜品明细能否从授权 API 获得（决定 §6.4/6.5 可行性）？
4. 与饮品垂直是**同一 App 内两个 Tab**，还是独立产品线？（影响信息架构）
