# 饮品比价系统 · 真实上线需求文档（PRD）

- **文档版本**：v1.0
- **状态**：评审中
- **适用阶段**：真实数据上线首期（试点城市）
- **前置依赖**：三大开放平台 API 授权（上线计划阶段 0）、ICP 备案
- **关联文档**：[上线计划.md](上线计划.md) · [设计文档.md](设计文档.md)（当前 Mock 系统 v0.4.2，本 PRD 在其能力之上定义真实数据要求）

---

## 1. 目标与范围

### 1.1 本期目标

在试点城市内，让用户**基于真实位置**搜索**真实实时**的饮品价格，得到**按地点排名的商户列表**与同商户跨平台到手价比价。

### 1.2 前期范围限制（本 PRD 的边界）⭐

| 维度 | 限制 | 说明 |
| --- | --- | --- |
| 商户 | **每个商圈网格 Top 20 商户** | 按综合排名选取（见 §4.3），非全城 Top 20（评估见 §7）|
| 商品 | **每商户 Top 50 SKU**（现制业态全菜单，≤60）| 按销量/热度选取（评估见 §7）|
| 城市 | 1 个试点城市，3~5 个核心商圈 | 数据配额与匹配质量可控 |
| 品类 | 饮料/饮品 | 与现有引擎一致 |

### 1.3 本期不做

代下单/支付、评价 UGC、多城市、饮品外品类、价格历史曲线。

## 2. 核心用户故事

1. 我在望京上班，打开页面自动定位（或手动选商圈），看到**附近可送达的**饮品商户按综合排名排列；
2. 我搜「生椰拿铁」，结果**只包含能送到我位置的商户**，价格是**当前真实价格**；
3. 我点开一个商品，看到三平台**此刻**的到手价对比与新鲜度标注，点「去下单」跳转对应平台；
4. 价格如果几分钟内变过，界面明确告诉我数据是几分钟前的，下单前有二次提示。

## 3. 功能需求 A：真实实时搜索

### 3.1 「真实」的定义

- **FR-A1（M）** 搜索结果全部来自**平台官方 API 授权数据**，禁止使用演示/伪造数据；每条价格必须可回溯到抓取批次（批次号 + 时间戳）。
- **FR-A2（M）** 界面移除「Mock 数据」标注，替换为数据新鲜度标注（「价格更新于 X 分钟前」）。

### 3.2 「实时」的分级定义（关键口径）⭐

真实世界的"实时"必须分级，否则配额成本不可控：

| 层 | 内容 | 时效 SLA | 实现 |
| --- | --- | --- | --- |
| L1 搜索召回 | 商品名/商户/库存状态索引 | **≤ 5 分钟** | 近实时索引，调度刷新（现有 DataStore 刷新机制承接）|
| L2 列表价格 | 搜索结果页展示价 | ≤ 5 分钟（热点）/ ≤ 30 分钟（长尾）| 分级刷新：Top 商户高频、其余低频 |
| L3 比价详情 | 用户点击比价的那一刻 | **实时拉取（点击时调平台 API）**，超时 2s 降级为 L2 缓存价 + 新鲜度标注 | 按需实时，杜绝"看到的和下单的不一样" |
| L4 下单前 | 跳转前提示 | 提示「以平台实际结算为准」| 合规兜底 |

- **FR-A3（M）** 按上表实现三级数据链路；L3 实时拉取失败时**必须降级可用**（旧价 + 显著新鲜度提示），不允许白屏。
- **FR-A4（M）** 搜索体验保持现有标准：输入即搜（防抖）、相关度排序、分页；P95 ≤ 800ms（索引查询，不含 L3）。
- **FR-A5（S）** 无结果兜底：搜索无结果时提示最接近的可得商品，并记录无结果查询日志（作为扩容依据，见 §7）。

## 4. 功能需求 B：基于地点的排名

### 4.1 位置获取

- **FR-B1（M）** 三种定位方式按优先级：浏览器/App 定位（**明示授权**，PIPL 合规，见 §6）→ 手动选择商圈 → 默认试点城市中心商圈。拒绝授权不阻塞使用。
- **FR-B2（M）** 位置以「商圈网格」为服务单元（试点期 3~5 个网格，网格半径约 3km 对齐即时配送半径）；用户位置映射到网格后使用网格数据，**个人精确坐标不落库**（只存网格 ID，隐私最小化）。

### 4.2 地理过滤（排名的前提）

- **FR-B3（M)** 只展示**配送范围覆盖用户位置**的商户门店（各平台配送范围以 API 返回为准）；范围外商户不出现在搜索与排名中。
- **FR-B4（M）** 同品牌多门店按**距离最近且可送达**的门店参与比价（商户主数据映射，同店跨平台对齐）。

### 4.3 商户排名规则（每网格 Top 20 的选取与展示序）

- **FR-B5（M）** 综合排名分 = 加权（初始权重，上线后按点击/转化调参）：

```
排名分 = 0.35 × 平台覆盖度（3平台=1.0 / 2平台=0.6）   ← 可比性是本产品核心价值
       + 0.25 × 销量分位（该网格内月售归一化）
       + 0.20 × 距离衰减（0-1km=1.0，线性衰减至 3km=0.2）
       + 0.20 × 评分归一化
```

- **FR-B6（M）** 每网格按排名分取 **Top 20 商户**入库采集；界面商户列表/商户直达按排名分排序，标注距离与预计送达时长。
- **FR-B7（S）** 排名因子与权重后台可配、可灰度；记录排名曝光→点击→跳转漏斗用于调参。
- **FR-B8（C）** 用户可切换排序：综合 / 距离优先 / 比价可省金额优先。

### 4.4 商品选取规则（每商户 Top 50）

- **FR-B9（M）** 现制业态（茶饮/咖啡）：**全菜单**（实际普遍 ≤ 60 款，不截断核心菜单）；商超/便利业态：饮品类目**销量 Top 50** SKU。
- **FR-B10（M）** 选品每周重算一次；用户搜索无结果日志中高频出现的 SKU 优先补录（人工审核入池）。

## 5. 非功能需求

| 类别 | 要求 |
| --- | --- |
| 性能 | 搜索 P95 ≤ 800ms；比价 L3 实时拉取 P95 ≤ 2s（超时降级）|
| 新鲜度 | 按 §3.2 分级 SLA，`price_as_of` 全链路透出 |
| 准确性 | 展示到手价 vs 平台实际下单价：误差 ≤2% 或 ≤1 元；抽样自动校验，超阈值自动降级「仅供参考」并告警 |
| 可用性 | 核心链路 ≥ 99.5%；单平台 API 故障单边降级 |
| 配额 | 平台 API 调用预算独立监控，达 80% 告警、达 100% 冻结低优先级刷新（保 L3）|
| 可观测 | 现有 /metrics 基础上增加：抓取成功率、价格误差分布、无结果率、各网格覆盖率 |

## 6. 合规需求（上线硬门槛）

- **C1（M）** 定位授权：明示弹窗 + 隐私政策（个保法 PIPL）；仅存网格 ID 不存精确坐标；提供关闭入口。
- **C2（M）** 文案合规：全站禁用「最便宜/最低价」绝对化用语（广告法），统一为「本次比价最低」；
- **C3（M）** 数据来源合规：仅使用授权 API；每类数据的使用范围不超出平台开发者协议；
- **C4（M）** ICP 备案完成后方可公网发布；页面公示比价口径说明。

## 7. 前期限制（Top 20 商户 / 50 商品）合理性评估 ⭐

### 7.1 量化测算

**数据规模**（按 4 网格试点）：

```
4 网格 × 20 商户 × ≤50 SKU × 3 平台 ≈ 最多 12,000 条价格条目
刷新负载（最重情形）：
  L2 热点(Top5商户×4网格×50SKU×3平台=3000条, 5min) ≈ 86万次/天
  → 明显超一般配额，须按「批量接口 + 增量变更」实现，
    按批量每次100条计 ≈ 8,640 批次/天 —— 在主流开放平台配额内可行
L3 实时拉取按点击量计（试点期日均千级）→ 可忽略
```

**覆盖率**（行业常识判断，上线后用数据验证）：即时零售/外卖订单高度头部集中，**单商圈 Top 20 商户通常覆盖 75%~85% 的饮品订单**；现制业态全菜单 + 商超 Top 50 SKU 预计覆盖该商户 85%+ 的饮品销量。

### 7.2 结论：**方向合理，需三处修正**

| 原始限制 | 评估 | 修正建议（已写入 §1.2/§4）|
| --- | --- | --- |
| 「前 20 名商户」 | ⚠️ 若按**全城** Top 20，用户所在商圈可能只剩三五家可送达 → 体验崩坏 | 改为**每商圈网格 Top 20**（4 网格 = 全城 60~80 家，规模仍可控）|
| 「50 个商品」 | ⚠️ 若指**全局共 50 个**商品 → 严重不足（一家便利店饮品区就上百 SKU，搜索无结果率会极高）；若指每商户 50 → 对商超合理、对现制会切掉菜单尾部 | 明确为**每商户 Top 50**，且现制业态放宽为全菜单（≤60）|
| 一刀切固定 | ⚠️ 静态名单会漂移（新店/爆品）| 每周重算 + 无结果日志驱动补录（FR-B10）|

### 7.3 上线后的验证指标（限制是否真的够用，让数据说话）

| 指标 | 健康线 | 触发动作 |
| --- | --- | --- |
| 搜索无结果率 | < 15% | 超线 → 扩商品池（50→80）|
| 「想比的商户不在列表」反馈率 | < 10% | 超线 → 扩商户池（20→35/网格）|
| Top20 商户订单跳转占比 | > 75% | 低于线说明选取规则失准 → 调 §4.3 权重 |
| 配额使用率 | < 70% | 有余量时优先加密热点刷新频率 |

### 7.4 放量路线

试点验证 4 周后按指标决策：20 商户/网格 → 35 → 全量可送达商户；50 SKU → 80 → 类目全量。**架构无需改动**（现有引擎已支持任意规模，限制只是采集侧的池子大小）。

## 8. 里程碑与验收

| 里程碑 | 内容 | 验收标准 |
| --- | --- | --- |
| R1 数据打通 | 首个授权平台真实适配器 + Top20/50 采集管道 | 单网格真实数据全链路跑通，价格误差抽检 ≤2% |
| R2 地点排名 | 定位/网格/配送过滤/排名分 | 网格内排名可解释、范围外商户 0 泄漏 |
| R3 实时化 | L1–L4 分级实时链路 | L3 点击实时价 P95 ≤2s，降级路径演练通过 |
| R4 试点发布 | 4 网格公开发布 | §7.3 四项指标全部达健康线，合规四项（§6）全过 |

## 9. 风险

| 风险 | 缓解 |
| --- | --- |
| 平台 API 授权范围不含价格/配送范围字段 | 授权谈判时按 §3/§4 字段清单核对；缺字段则该能力降级并重估限制 |
| 配额低于测算 | L2 刷新降频 + 收缩网格数，保 L3 实时 |
| 商户主数据映射错误（同店异名）| 上线前人工全量审核 Top20×4 网格（≤80 家，人工可行——这也是前期限制的隐性收益）|
| 排名被质疑不公 | 排名规则公示 + 因子可解释展示 |
