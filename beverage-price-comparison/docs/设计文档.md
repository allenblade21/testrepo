# 饮品比价系统 · 设计文档

- **版本**：v0.1（设计阶段）
- **范围**：对 **阿里闪购 / 京东 / 美团** 三个平台上的**饮料饮品**进行比价
- **目标**：用户搜索一款饮品，系统展示三个平台的**到手价**并排对比，标出最便宜方

---

## 1. 目标与范围

### 1.1 要做的

- 比价平台：**阿里闪购、京东、美团**（三方）
- 品类：**饮料 / 饮品**
  - 瓶装/罐装标品（可乐、矿泉水、瓶装茶饮/果汁…）
  - 现制饮品（奶茶、咖啡、鲜榨…）
- 核心能力：饮品搜索 → 跨平台同款匹配 → 到手价计算 → 三方并排比价 → 标注最优

### 1.2 本期不做

- 不做代下单/代付（仅展示与跳转）
- 不做饮品以外品类
- 不做真实平台实时抓取（先用 Mock 数据，适配器可插拔，见 §4）

---

## 2. 为什么饮品比餐饮外卖更好比

饮品品类**标准化程度高**，跨平台匹配天然更可靠：

| 类型 | 匹配主键 | 匹配强度 |
| --- | --- | --- |
| 瓶装/罐装标品 | 条码 / 品牌 + 规格（容量）| 强（精确匹配）|
| 现制饮品 | 品牌 + 品名 + 规格（杯型/糖冰）| 中（语义匹配）|

这让「同一款饮品在三个平台」的对齐比之前的餐品比价可靠得多。

## 3. 系统架构

```
┌───────────────────────────────────────────────┐
│  前端页面（搜索饮品 → 三平台并排比价展示）      │
└───────────────────────────────────────────────┘
                    │ HTTP
┌───────────────────────────────────────────────┐
│  FastAPI 接口层   GET /search   GET /compare   │
└───────────────────────────────────────────────┘
                    │
┌───────────────────────────────────────────────┐
│  业务核心                                       │
│   比价编排  ·  匹配引擎  ·  到手价引擎          │
└───────────────────────────────────────────────┘
                    │ 统一适配器接口 PlatformAdapter
     ┌──────────────┼───────────────┐
 ┌────────┐    ┌────────┐      ┌────────┐
 │阿里闪购│    │  京东  │      │  美团  │   ← 可插拔适配器
 │Adapter │    │Adapter │      │Adapter │     当前=Mock 实现
 └────────┘    └────────┘      └────────┘
                    │
┌───────────────────────────────────────────────┐
│  SQLite 种子数据（饮品 / 各平台价格 / 优惠）    │
└───────────────────────────────────────────────┘
```

### 3.1 分层职责

- **前端**：搜索框 + 结果卡片（三平台到手价并排、最优高亮、明细展开）。
- **接口层（FastAPI）**：`/search` 关键词召回可比饮品；`/compare` 返回某饮品三平台到手价。
- **业务核心**：
  - *匹配引擎*：把三平台的条目对齐成一个「可比饮品单元」。
  - *到手价引擎*：售价 + 优惠 + 配送费 → 到手价（口径见 §6）。
  - *比价编排*：聚合三平台结果，计算最优与节省。
- **适配器层**：统一接口 `PlatformAdapter`，每平台一个实现。**当前为 Mock**（读 SQLite 种子数据），将来替换为官方 API / 合规采集，**上层不变**。

---

## 4. 数据来源策略（关键决策）

三大平台无公开免费比价接口，真实数据需授权/合规采集。为保证**沙盒内即可跑、可测**：

- **MVP 采用「适配器 + Mock 数据」**：内置一批真实感的饮品价格与优惠种子数据，匹配/算价/比价/展示**全链路真实可运行**。
- **适配器可插拔**：`PlatformAdapter` 接口稳定，未来接真实数据源只替换实现类，业务层零改动。
- **合规前置**：真实数据阶段优先官方/合作 API；采集方案须先过合规评审。

---

## 5. 数据模型

```
Platform      平台          id, name(阿里闪购/京东/美团)
Beverage      可比饮品单元   id, canonical_name, brand, spec, type(bottled/made), barcode?
Listing       平台商品条目   id, platform_id, beverage_id, title, list_price, sale_price, stock
Promotion     优惠          id, listing_id, type(满减/直降/多件/平台补贴/券), threshold, value, stackable
DeliveryFee   配送计费      platform_id, base_fee, fee_reduction, min_order
```

- `Beverage` 是三平台对齐的桥梁；`Listing` 是各平台原子数据。
- 金额统一以「分」存储，展示换算为「元」。

---

## 6. 到手价计算口径

```
单平台到手价 =
    售价(sale_price) × 数量
  − 平台补贴
  − 满减 / 多件优惠（如第二件半价）
  − 可用优惠券（按可叠加规则）
  + 配送费 − 配送费减免
  （现制饮品：未达起送价则不可下单，需提示）
```

- 输出**结构化明细**（售价→各项优惠→配送→到手价），前端透明展示。
- 规则可配置，不硬编码（各平台优惠叠加规则不同）。

## 7. 接口设计（草案）

| 接口 | 方法 | 入参 | 出参 |
| --- | --- | --- | --- |
| `/search` | GET | `q`（关键词）, `city?` | 匹配到的可比饮品列表 |
| `/compare` | GET | `beverage_id`, `qty?`, `city?` | 三平台到手价 + 明细 + 最优 + 节省 |
| `/health` | GET | - | 服务健康检查 |

`/compare` 返回示例（结构示意，数值为演示）：

```json
{
  "beverage": {"name": "可口可乐 330ml×6", "brand": "可口可乐"},
  "platforms": [
    {"platform": "阿里闪购", "final_price": 1290, "breakdown": {...}},
    {"platform": "京东",     "final_price": 1180, "breakdown": {...}},
    {"platform": "美团",     "final_price": 1350, "breakdown": {...}}
  ],
  "cheapest": "京东",
  "savings_vs_max": 170
}
```

## 8. 技术选型

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 后端 | Python + FastAPI | 轻量、自带 OpenAPI 文档、沙盒秒起 |
| 存储 | SQLite（种子数据）| 零配置，克隆即跑 |
| 前端 | 原生 HTML + JS（单页）| 比价并排展示，Chromium 可直接演示 |
| 适配器 | 统一接口 + Mock 实现 | 可插拔，未来接真实数据 |
| 测试 | pytest | 覆盖匹配与算价核心逻辑 |
