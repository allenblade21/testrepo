## 1. 目标与非目标

### 1.1 G-R1 目标
1. 落地团购**数据模型**（`GroupDeal / MenuItem / UsageRule / Restaurant / ComparableDeal`），金额用分。
2. 接入**单平台（美团点评）团购适配器**——G-R1 用 **Mock 实现**，契约对齐真实「联盟/CPS」可得字段。
3. 打通**单平台链路**：取数 → 建门店/套餐索引 → 构建可比单元（同门店约束）→ 团购到手价 → 单平台结果输出。
4. 一套**Mock 种子 + pytest 场景 + 哨兵**，锁住数据构成与到手价口径。

### 1.2 G-R1 非目标（明确不做）
- 跨平台套餐语义匹配（G-R2）；多平台并排比价界面（G-R3）；划线价/核销合规评审与发布（G-R4）。
- 真实联盟 API 对接（等权限；G-R1 只做契约对齐的 Mock）。
- 代金券（Voucher）到手价、多套餐组合建议（后续）。

## 2. 总体架构（复用主系统骨架）

团购垂直**不另起系统**，作为主应用内的并列模块，最大化复用（PRD §4、ADR-012）：

```
                    ┌───────────────── 同一 App（双 Tab，ADR-012）─────────────────┐
   饮品即时零售 Tab ─┤  共用：账户 / 定位·商圈网格 / 导出PDF / 前端壳 / 生产化中间件  ├─ 团购团餐 Tab
                    └──────────────────────────────────────────────────────────────┘
                                                  │
   团购模块（G-R1 新增）                          ▼
   ┌────────────────────────────────────────────────────────────────────┐
   │ TuangouAdapter(Mock)  →  DealStore.rebuild()  →  build_comparable_deals() │
   │   （联盟/CPS 字段契约）      （门店/套餐索引）      （同门店约束+可比单元）    │
   │                                   │                                        │
   │                          tuangou_pricing（团购到手价引擎，复用封顶不变式）    │
   │                                   │                                        │
   │                          /api/tuangou/*（search / restaurants / compare）  │
   └────────────────────────────────────────────────────────────────────┘
```

**复用**（不改）：`PlatformAdapter` 契约范式、`DataStore` 可重建快照范式、`geo`（网格/排名）、`export_pdf`、config/中间件（限流/可观测/CORS）。
**新增**：`tuangou/` 子模块（模型、适配器、匹配、到手价、路由、种子）。与饮品模块**下层数据隔离、上层壳复用**。

## 3. 数据模型（金额用分）

新增 `app/tuangou/models.py`：

```
Restaurant       餐厅门店
  id            门店唯一 ID（比价边界字段，等价饮品 merchant，不可去）
  brand         品牌（如「海底捞」）
  branch        门店名（如「中关村店」）
  cuisine       菜系（火锅/烧烤/正餐…）
  grid_id       商圈网格（复用 geo）
  lat, lng      坐标（仅解析用，不落库——复用 ADR-006 隐私最小化）
  rating        评分
  avg_price_cents 人均参考价（分）

MenuItem         套餐内菜品项
  name          菜名
  spec          份量/规格（如「2 份」「500ml」）
  qty           数量
  is_gift       是否赠品

UsageRule        使用规则（团购特有）
  time_windows      可用时段（如 ["工作日","避开节假日"]）
  need_reserve      是否需预约
  per_table_limit   每桌可用张数
  extra_fee_cents   包间费/服务费/茶位费（分，不含在团购价内的加项）
  stackable_voucher 能否叠加代金券
  refund_policy     退款政策（随时退/过期退…）

GroupDeal        团购套餐（可比单元的成员）
  id            套餐 ID
  restaurant_id 所属门店（外键，比价边界）
  platform      平台（枚举：meituan / douyin / koubei / xhs / kuaishou）
  title         套餐标题
  deal_type     套餐 / 代金券（G-R1 只做套餐）
  party_size    适用人数区间 (min,max)
  list_price_cents  门市价/划线价（分，合规敏感，PRD §9）
  group_price_cents 团购价（分）
  subsidy_cents     平台补贴/神券可减（分）
  menu_items    List[MenuItem]
  usage_rule    UsageRule
  deeplink      跳转下单链接（联盟 CPS 带参，PRD 转化闭环）
  price_as_of   价格快照时间（团购时效性强）

ComparableDeal   可比套餐单元
  id            单元 ID（内容哈希派生，重建不改已有 ID——复用 store 范式）
  restaurant_id 门店（单元内唯一——同门店约束）
  party_size    对齐的人数档
  deals         List[GroupDeal]（G-R1 单平台=1 条；G-R2 起多平台）
  match_confidence  精确/疑似/单平台（G-R1 恒为「单平台」）
```

> **金额字段一律 `_cents` 整数**（铁律 1）。展示层 `分→元` 换算沿用饮品前端工具。

## 4. 取数与适配器设计

### 4.1 适配器契约（对齐联盟/CPS 可得字段）
`TuangouAdapter` 沿用 `PlatformAdapter` 范式（ADR-002）：G-R1 为 `MockMeituanTuangouAdapter`，读固定种子，**但字段集严格对齐美团联盟「团单/商品查询」可得字段**——标题、团购价、门市价、门店、人数、deeplink 为**主字段**；`menu_items/usage_rule` 为**可能缺失字段**，Mock 中部分置空以演练降级（见 §7、CPS 手册 §5）。

### 4.2 字段映射与降级
| 目标字段 | 联盟可得性 | 缺失时 |
| --- | --- | --- |
| 门店 / 标题 / 团购价 / 门市价 / 人数 / deeplink | 主字段，较可得 | — |
| `menu_items`（菜品清单/份量）| ⚠️ 未必在授权范围 | 置空 → `has_menu_detail=false`，界面标注「未含菜品明细」，匹配退化 |
| `usage_rule.extra_fee_cents` 等 | 视平台 | 缺则不计入到手价并标注「口径可能不含附加费」 |

> 降级不是 bug：字段可得性由授权决定，系统必须**如实标注**而非假装完整（呼应 PRD §10、§12）。

## 5. 可比单元构建与同门店约束（复用三层保障）

沿用饮品 ADR-001 的三层保障，把边界字段从 `merchant` 换成 `restaurant_id`：

1. **匹配键**：可比单元键第一段永远是 `restaurant_id`（+ `party_size` 档）。
2. **构建断言**：`build_comparable_deals()` 断言单元内所有 `GroupDeal.restaurant_id` 唯一，否则抛错。
3. **接口校验**：`/api/tuangou/compare` 传入跨门店套餐集合 → 返回 **409**。

> G-R1 单平台，每个可比单元只含 1 条 deal（`match_confidence=单平台`）；约束代码此刻虽不跨平台触发，但**必须就位**，为 G-R2 多平台匹配铺好硬边界。

## 6. 团购到手价引擎（复用封顶不变式）

新增 `app/tuangou/pricing.py`，口径按 PRD §7：

```
套餐到手价_cents =
    group_price_cents
  − subsidy_cents（按可叠加规则，封顶于当前应付、不得为负——复用饮品 min() 不变式）
  + usage_rule.extra_fee_cents（若该套餐收取且不含在内）

人均到手价_cents = round(套餐到手价_cents / 适用人数)
   （人数取用户所选；未选取 party_size 区间中值）
```

- **复用饮品引擎的核心不变式**：每项减免 `min(amount, current_payable)`，到手价恒非负（勿删，有测试锁）。
- **团购新增项**：`extra_fee` 是**加项**（饮品没有），**人均** = 到手价 ÷ 人数（饮品没有）。
- 输出**明细对账**：团购价 → 减补贴 → 加附加费 → 到手价 → 人均，逐行可解释（复用饮品明细范式）。

## 7. API 设计（`/api/tuangou/*`，复用 ADR-009 分路径约定）

| 端点 | 方法 | 说明 |
| --- | --- | --- |
| `/api/tuangou/restaurants` | GET | 按位置/网格/菜系/人数召回门店（复用 geo 排名）|
| `/api/tuangou/search` | GET | 按餐厅名/菜系/人数搜套餐，相关度+分页（复用搜索范式）|
| `/api/tuangou/compare` | POST | 传可比单元 ID / 或门店+人数，返回单平台到手价+人均+明细+使用规则；跨门店 **409** |
| （页面）`/tuangou` | GET | 团购 Tab 页面（G-R3 完善，G-R1 可先占位）|

> 页面走 `/tuangou`，数据走 `/api/tuangou/*`——**沿用 ADR-009**，页面与 API 不同路径，避免 FastAPI 路由遮蔽。

## 8. Mock 种子数据设计

新增 `app/tuangou/seed_deals.py`（固定种子，可复现，承载测试场景基线，**永不随机重生成**——复用 seed_data 纪律）：

| 场景 | 设计 |
| --- | --- |
| 正常套餐 | 某火锅店「4 人套餐」，含完整菜品清单+使用规则+补贴 |
| 附加费场景 | 某正餐「包间套餐」，`extra_fee_cents` > 0，验证加项 |
| 菜品明细缺失 | 某店套餐 `menu_items=[]`，`has_menu_detail=false`，演练降级标注 |
| 人数区间 | 「3-5 人套餐」，验证未选人数时取中值(4)算人均 |
| 划线价 | 门市价 > 团购价，标注为 Mock、合规占位 |

- **哨兵**：`test_tuangou_seed_sentinel` 钉死门店数/套餐数/缺明细数，改动数据即报警（复用 catalog 哨兵纪律）。
- **诚实标注**：所有价格为 Mock 演示数据，界面「非真实价格」标注不得移除（铁律 5）。

## 10. G-R1 工作分解（落地顺序）

1. 建 `app/tuangou/` 骨架 + `models.py`（模型 + 分存储）。
2. `seed_deals.py` 固定种子（覆盖 §8 场景）。
3. `MockMeituanTuangouAdapter`（字段契约 + 降级）。
4. `DealStore.rebuild()` + `build_comparable_deals()`（同门店约束三层）。
5. `pricing.py`（团购到手价 + 人均 + 明细）。
6. `/api/tuangou/*` 路由挂载到主 app。
7. `tests/tuangou/*` + 哨兵，跑全绿。
8. 更新 CHANGELOG / 状态看板；必要时补复盘。

## 12. 风险与未决（承接 PRD，接入前确认）

- 联盟 API 是否对**比价类**应用发权限、deeplink 能否用于第三方比价（CPS 手册 §7 待确认清单）——不阻塞 G-R1 Mock，但阻塞真实接入。
- `menu_items` 字段真实可得比例未知 → 降级路径必须先建好（本设计已内建）。
- 团购价时效性强 → `price_as_of` 与刷新策略 G-R2/R3 细化。
