# 比价系统 · 产品需求文档（PRD）

- **文档版本**：v0.1（初稿）
- **状态**：评审中
- **适用范围**：MVP 阶段（阿里闪购 + 美团餐饮速递）
- **关联文档**：[系统架构.md](系统架构.md) · [数据字典.md](数据字典.md)

---

## 1. 背景与目标

### 1.1 背景

即时零售/餐饮外卖已进入多平台竞争阶段。同一家门店、同一份餐品或同一件商品，在**阿里闪购**（淘宝闪购/淘宝小时达即时零售）与**美团**（外卖/闪购速递）两个平台上，因为**平台补贴、店铺优惠券、满减、配送费、会员权益、起送价**等差异，最终「到手价」往往并不相同。用户很难在下单前快速判断「哪个平台更便宜」。

### 1.2 产品目标

打造一个**下单前的到手价比价工具**：用户输入位置与想要的商品/餐品，系统在两个平台之间检索、匹配、计算真实到手价，并给出可直接跳转下单的比价结果。

### 1.3 成功指标（北极星与关键指标）

| 指标类型 | 指标 | MVP 目标 |
| --- | --- | --- |
| 北极星 | 通过比价产生的跳转下单转化次数 | 建立基线 |
| 匹配质量 | 同款商品/餐品匹配准确率 | ≥ 90% |
| 价格准确 | 展示到手价与实际下单价误差 | ≤ 2% 或 ≤ 1 元 |
| 覆盖度 | 试点城市门店/SKU 覆盖率 | ≥ 70% |
| 时效 | 单次比价请求 P95 响应 | ≤ 2s |
| 数据新鲜度 | 价格数据滞后 | ≤ 5 分钟（热点）/ ≤ 30 分钟（长尾）|

### 1.4 非目标（本期不做）

- 不做代下单/代付（仅跳转至平台原生 App/小程序完成交易）。
- 不做除阿里闪购、美团以外的平台（京东秒送、饿了么等后续迭代接入）。
- 不做全国全城覆盖，先在 1~2 个试点城市验证。
- 不做商品评价/UGC 内容社区。

## 2. 用户与场景

### 2.1 目标用户

| 画像 | 核心诉求 |
| --- | --- |
| 价格敏感型用户 | 每单都想选最便宜的平台 |
| 家庭日常采买用户 | 生鲜/商超即时零售的多平台比价 |
| 上班族点餐用户 | 午晚高峰快速决策，省钱又省时 |

### 2.2 核心用户故事

- 作为用户，我想搜索「一点点·招牌奶茶」，看到它在阿里闪购和美团的到手价对比，以便选更便宜的平台下单。
- 作为用户，我想按当前定位查看附近某家门店在两个平台的价格差异。
- 作为用户，我想把某商品加入「比价清单」，一次性看到整单在两个平台各自的合计到手价。
- 作为用户，我希望到手价包含所有优惠和配送费后的**真实金额**，而不是只看标价。

## 3. 功能需求

需求优先级采用 MoSCoW：**M**(必须) / **S**(应该) / **C**(可以) / **W**(暂不)。

### 3.1 定位与门店发现（M）

- FR-1（M）：支持定位/手动输入收货地址，作为比价的地理基准。
- FR-2（M）：基于地址返回两个平台在配送范围内、可送达的门店列表。
- FR-3（S）：门店按品牌/品类聚合，标识两平台是否**同店可比**。

### 3.2 商品/餐品搜索与匹配（M）

- FR-4（M）：支持按关键词搜索商品/餐品。
- FR-5（M）：**跨平台同款匹配**——将阿里闪购与美团上代表「同一 SKU/同一餐品」的条目关联为一个「可比单元」。
- FR-6（S）：匹配置信度分级展示（精确匹配 / 疑似匹配 / 仅单平台可得）。
- FR-7（C）：对无法自动匹配的条目支持人工/运营标注与纠错。

### 3.3 到手价计算（M）— 核心

- FR-8（M）：对每个平台分别计算**到手价**，公式见 §3.3.1。
- FR-9（M）：明细透明展示：标价、店铺优惠、平台补贴、满减、红包/券、配送费、包装费、起送差额。
- FR-10（S）：区分**单品到手价**与**整单到手价**（考虑满减门槛、起送价、跨店叠加）。
- FR-11（S）：标注价格有效期与「可能受时段/库存影响」的提示。

#### 3.3.1 到手价计算口径

```
单平台整单到手价 =
    Σ(商品标价 × 数量)
  − 店铺优惠（满减/直降/第二份半价等）
  − 平台补贴/大额红包
  − 可用优惠券（店铺券 + 平台券，按可叠加规则）
  + 配送费（含距离/时段/小费加价，减去配送费减免）
  + 打包/餐盒费
  + 起送差额说明（未达起送价时不可下单，需提示）
  − 会员权益折扣（可选，见 §3.5）
```

> 计算引擎需支持**规则可配置**：不同平台的券叠加规则、满减计算顺序、补贴触发条件不同，须以规则表驱动而非硬编码。

### 3.4 比价展示（M）

- FR-12（M）：并排展示两平台到手价，明确标注「更便宜方」及**节省金额/比例**。
- FR-13（M）：一键**跳转对应平台** App/小程序完成下单（Deeplink）。
- FR-14（S）：展示除价格外的关键决策因素：预计送达时长、配送费、评分、起送价。
- FR-15（C）：比价清单（购物车式）——多商品合并比价，输出整单更优平台。

### 3.5 用户账户与个性化（S/C）

- FR-16（S）：登录后可保存常用地址、比价历史、收藏门店。
- FR-17（C）：录入用户在各平台的**会员身份**（如美团神会员、淘宝88VIP），用于更精准的到手价（会员价/免配送费）。
- FR-18（W）：价格订阅与降价提醒（后续迭代）。

### 3.6 运营与配置后台（M）

- FR-19（M）：平台接入配置、抓取/接口任务调度与监控。
- FR-20（M）：匹配规则、到手价规则、券叠加规则的可视化配置。
- FR-21（S）：数据质量看板（覆盖率、匹配率、价格误差、任务失败率）。

## 4. 非功能需求（NFR）

| 类别 | 要求 |
| --- | --- |
| 性能 | 比价查询 P95 ≤ 2s；门店列表 ≤ 1s |
| 数据新鲜度 | 热点 SKU ≤ 5 min，长尾 ≤ 30 min |
| 可用性 | 核心比价链路可用性 ≥ 99.5% |
| 一致性 | 展示到手价与真实下单价误差 ≤ 2% 或 ≤ 1 元，超阈值需降级为「价格仅供参考」 |
| 扩展性 | 新增一个平台的接入成本 ≤ 2 人周（依赖适配层抽象） |
| 弹性 | 单平台数据源故障时，降级为单边展示而非整体不可用 |
| 安全合规 | 见 §6 |
| 可观测 | 全链路日志/指标/告警，价格异常自动熔断 |

## 5. 数据需求与「细节输入」

比价的准确性完全取决于输入数据的完整度。下列为**每个可比单元必须采集的关键输入字段**，完整字段定义见 [数据字典.md](数据字典.md)。

### 5.1 地理/上下文输入（用户侧）

- 收货地址 / 经纬度、城市、下单时段（影响配送费与时效）。
- 用户各平台会员身份（可选，影响会员价/免配送）。

### 5.2 门店维度输入（平台侧）

- 平台门店 ID、品牌、品类、营业状态、配送范围、起送价、基础配送费、评分、预计送达时长。

### 5.3 商品/餐品维度输入（平台侧）—— 比价核心

| 字段 | 说明 | 是否必须 |
| --- | --- | --- |
| 平台 SKU/餐品 ID | 平台内唯一标识 | 必须 |
| 名称 / 规格 / 单位 | 用于跨平台匹配 | 必须 |
| 品牌 / 条码（商超类）| 强匹配依据 | 商超类必须 |
| 标价（原价）| 计算基准 | 必须 |
| 当前售价 | 平台/店铺直降后价格 | 必须 |
| 规格属性（口味/大小/份量）| 保证「同款」 | 必须 |
| 库存/可售状态 | 影响可比性 | 必须 |
| 图片 | 辅助匹配与展示 | 应该 |

### 5.4 优惠/费用维度输入（到手价关键）

- 店铺优惠（满减、直降、第 N 份优惠、限时秒杀）。
- 平台补贴/大额红包及触发条件。
- 可用优惠券（券面额、门槛、可叠加规则、有效期、适用范围）。
- 配送费（基础费、距离加价、时段加价、配送费减免）。
- 打包费/餐盒费、起送价。
- 会员权益（会员价、免配送、专属券）。

> 这些「优惠/费用输入」是到手价计算的核心变量，也是各平台差异最大、最易出错的部分，需要在数据字典中逐项建模并支持规则化配置。

## 6. 合规、风险与数据来源

### 6.1 数据获取策略（重要）

- **优先**使用平台官方开放接口/合作 API（若可获得授权）。
- 无官方接口时，评估合规抓取方案：遵守 robots 协议与各平台服务条款、控制频率、不绕过技术保护措施、不存储用户隐私数据。
- **法律与合规须在实现前评审**（数据授权、反不正当竞争、著作权、平台条款）。本文档不预设采用任何违反平台条款的手段。

### 6.2 主要风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 平台接口/页面结构变更 | 数据中断 | 适配层隔离 + 监控告警 + 快速修复 |
| 到手价算错（券规则复杂）| 误导用户、信任受损 | 规则表驱动 + 抽样校验 + 误差熔断降级 |
| 数据授权/合规风险 | 法律风险 | 合规前置评审、优先官方合作 |
| 平台限流/封禁 | 覆盖率下降 | 合规频控、单边降级、缓存 |
| 价格实时性不足 | 展示与实际不符 | 分级新鲜度 + 下单前二次校验提示 |

## 8. 未决问题（Open Questions）

1. 官方 API 授权可获得性如何？决定数据来源策略与合规边界。
2. 首批试点城市与品类如何选择（餐饮 vs 商超即时零售优先级）？
3. 会员身份信息如何在合规前提下获取与使用？
4. 到手价「下单前二次校验」是否可行（依赖跳转前的实时报价能力）？

> 附：本文档中涉及的平台优惠规则、接口能力均为设计假设，需在 M1 阶段以实际可获得的数据能力校准。
